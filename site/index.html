How Motus works.

A run is one command execution. A finding is what you choose to save about a failure: what happened, the likely cause, or what to try next.

A person, coding agent, script, or CI job calls the CLI from the workflow it already runs. By default, Motus writes recorded runs and findings to .motus/ledger.db. Anyone using that same ledger can search the records later.

  1. 01 Record

    Run a test, build, script, or tool through Motus.

    motus wrap -- ...
  2. 02 Add a finding

    Save what you learned and the next step worth trying.

    motus finding add
  3. 03 Link the fix

    After the fix works, link the finding to that successful run.

    motus finding close
  4. 04 Find later

    Search the finding and inspect both runs when the problem returns.

    motus finding list --query

Using a coding agent? Copy the project instructions that tell it when to search, record, and resolve findings.

Try the full workflow.

This example uses npm test. Replace it with any command you already run. Paths and IDs are shortened.

1

Install Motus

Use Go 1.26.5 or newer, or download a verified archive from GitHub Releases. Go installs the binary in GOBIN, or GOPATH/bin when unset. Put that directory on PATH.

Motus writes this project's ledger to .motus/ledger.db. Add .motus/ to .gitignore before recording work.

$ go install github.com/motus-os/work-ledger/cmd/motus@latest
$ motus version
2

Record the failing command

Motus prints a run ID. After a failure, it also prints the exact command for adding a finding.

$ motus wrap -- npm test
motus: recorded run_0370... (failure)
Keep why this failed:
  motus finding add --run run_0370... --file -
3

Save what you learned

Copy the printed command and add --format json. Paste a summary, likely cause, and next step, then finish input with Ctrl-D, or Ctrl-Z and Enter on Windows.

$ motus finding add --run run_0370... --format json --file -
{
  "summary": "The generated file was stale.",
  "hypothesis": "Generation was skipped.",
  "next_step": "Regenerate, then test."
}
Recorded finding_1457... (open)
4

Record the successful check

Fix the problem and run the same command again. Keep the new run ID if it succeeds.

$ motus wrap -- npm test
motus: recorded run_c588... (success)
5

Link and search

Use the finding ID and successful run ID. Enter a closure note, finish input the same way, then search your saved words.

$ motus finding close finding_1457... --disposition resolved --run run_c588... --file -
Refreshed the generated file before running the check.
Closed finding_1457... (resolved)

$ motus finding list --query stale

What Motus keeps.

Run facts are captured when you use motus wrap. Finding text is stored only when you add it.

Recorded with a run

  • stable run and event IDs
  • timestamps and duration
  • executable name and argument count
  • Git repository, commit, and dirty state
  • exit code, signal, timeout, and outcome
  • output byte and line counts

Written by you

  • finding summary and likely cause
  • next step, when useful
  • resolution or dismissal note
  • links to the failed and successful runs

Common questions.

Why not Git, shell history, or CI logs?
Git shows what changed. Shell history and CI show what ran. Motus keeps your explanation connected to both the failed and successful run, then makes that record searchable.
When is a finding worth saving?
When a failure took real investigation, crossed tools or sessions, or is likely to return. Routine failures do not need a finding.
Does Motus store raw command output?
No. Output continues to your terminal or CI log. Motus records counts and stores only the finding text you choose to add.
